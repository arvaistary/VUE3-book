# Конституция публичной frontend-книги

## Core Principles

### I. Публичная безопасность по умолчанию

Любой текст и пример считаются потенциально публикуемыми только после
проверки. Сведения, по которым можно восстановить закрытый проект, не должны
попадать в `public/`.

### II. Читатель важнее внутренней структуры источника

Книга объясняет понятия в порядке, удобном читателю. Структура внутреннего
курса является картой тем, но не обязана становиться оглавлением книги.

### III. Абстрагирование исходного проекта

Имена, пути, API и конфигурация исходного проекта заменяются обобщёнными
примерами. В книге остаются инженерная проблема, решение, ограничения и
проверяемый результат.

### IV. Парные примеры кода

Важные решения сопровождаются плохим и хорошим вариантом. Плохой вариант
должен быть намеренно ограниченным, безопасным для публикации и снабжённым
объяснением последствий.

### V. Доступный и точный язык

Термины вводятся до примеров, сленг не используется как замена объяснению,
а английское название сохраняется только там, где оно помогает читать код или
документацию.

### VI. Канонические артефакты

Решения по книге хранятся в активных `spec.md`, `plan.md` и `tasks.md`.
Рабочие заметки не заменяют эти документы и не могут противоречить им.

### VII. Проверяемая готовность

Готовность главы означает, что проверены содержание, примеры кода, ссылки,
форматирование и публичная граница. Текстовый маркер без воспроизводимой
проверки не считается доказательством.

## Workflow Requirements

- Для крупной работы использовать полный work item.
- Выполнять последовательность `clarify → plan → tasks → analyze` до
  написания глав.
- Использовать `workflow/core/` без изменений и адаптировать только
  `workflow/project/`.
- Не переносить в публичный текст внутренние пути и сведения о проекте.
- Перед публикацией запускать проверки project adapter-а.
- Не считать черновик опубликованным, пока он не прошёл редакторскую и
  конфиденциальную проверку.

## Governance

Изменения конституции требуют зафиксированного обоснования, обновления версии
и повторной проверки workflow.
