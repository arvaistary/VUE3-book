# Brief части 1. Как мыслить о frontend-системе

## Учебная цель

После части читатель сможет провести границу ответственности для небольшой
SSR-системы, отличить конфигурацию запуска от логики интерфейса и объяснить,
почему место кода влияет на пользовательский риск. Уровень — начинающий
frontend-разработчик с базовыми знаниями JavaScript и Vue.

## Аудитория и предпосылки

Читатель уже умеет читать функции, компоненты и простые HTTP-запросы. Знание
Nuxt желательно, но не обязательно: термины SSR и окружение будут объяснены в
тексте.

## Термины

Архитектура, граница ответственности, SSR (серверный рендеринг), runtime
configuration (конфигурация во время запуска), окружение, координирующий слой.

## Минимальная задача и пара примеров

Одна задача для обоих вариантов: получить адрес ресурса из конфигурации и
использовать его в прикладной операции, не смешивая это с разметкой. Плохой
вариант показывает адрес и сборку строки внутри UI; хороший отделяет
конфигурацию и прикладную функцию. Оба варианта работают только с синтетическим
ресурсом `articles`.

## Ограничения

Часть не является руководством по структуре конкретного Nuxt-репозитория и не
утверждает, что одна схема слоёв подходит приложению любого размера. Для
маленького виджета дополнительные границы могут быть избыточны.

## Критерии готовности

- читатель понимает путь запроса от окружения к пользовательскому результату;
- термины объяснены до кода;
- два примера решают одну задачу и используют вымышленные данные;
- названы цена разделения и случаи, когда оно не нужно;
- упражнение можно выполнить локально без внешнего сервиса.

## Источники и проверка

Технические понятия сверяются с [документацией Nuxt о directory
structure](https://nuxt.com/docs/guide/directory-structure/nuxt) и с
[документацией о runtime config](https://nuxt.com/docs/guide/going-further/runtime-config).
Код проверяется чтением и запуском функций Node.js из главы.
