# Часть 5. Производительность, SEO и внешние интеграции

## Ситуация и риск для пользователя

Пользователь открывает статью по ссылке из поиска и ждёт, пока загрузится
аналитика, виджет поддержки и несколько декоративных ресурсов. Основной текст
уже можно было показать, но экран остаётся пустым. Если же контент появляется
сразу, но затем долго не становится интерактивным, пользователь всё равно
считает страницу медленной.

## Учебная цель

После этой главы вы сможете отделить критический путь отображения страницы от
необязательной интеграции, поставить измеримую цель и объяснить, почему SSR
сам по себе не гарантирует быструю страницу. Нужны базовые JavaScript и
понимание Promise.

## Термины

**Критический путь** — операции, без которых нельзя показать полезный первый
экран. **SSR (server-side rendering, серверный рендеринг)** позволяет отдать
HTML с содержанием до полной активации JavaScript. **SEO (search engine
optimization, поисковая доступность)** зависит, в частности, от того,
получает ли робот понятный контент и метаданные.

**Отложенная загрузка** переносит некритичную работу на более поздний момент.
**Web Vitals** — набор пользовательских показателей, по которым можно
оценивать скорость и стабильность отображения. Их нужно измерять, а не
подменять общими обещаниями.

**Promise** — объект, представляющий результат асинхронной операции, который
может стать успешным или ошибочным позже.

**Планировщик (scheduler)** — функция, которая принимает работу и запускает
её позже. В этой главе предполагается, что `schedule` умеет обработать
отклонённый `Promise` этой работы и передать ошибку в наблюдаемость; иначе
отложенный сбой может стать необработанным исключением.

## Минимальная задача

Оба варианта загружают статью и регистрируют событие просмотра. Вход — три
функции: `loadArticle`, `sendMetric` и `schedule`. Результат — готовые данные
статьи. Локальная проверка сравнивает момент, когда функция возвращает статью,
с моментом отправки события.

## Плохой пример

Разработчик хочет не потерять аналитическое событие и поэтому ожидает его
вместе с данными страницы:

```js
async function loadPage(loadArticle, sendMetric) {
  const article = await loadArticle();
  await sendMetric({ type: 'article_view', id: article.id });
  return article;
}
```

Такой порядок понятен и действительно гарантирует, что событие отправлено до
возврата результата. Но если аналитический сервер медленный или недоступен,
основной текст задерживается. Для SSR это может означать лишнее время до
готового HTML, а на клиенте — более позднюю интерактивность. Надёжность
вторичной операции ошибочно поставлена выше видимого содержания.

## Хороший пример

Критичные данные возвращаются сразу после своей готовности. Вторичная работа
планируется отдельно и не блокирует отображение.

```js
async function loadPage(loadArticle, sendMetric, schedule) {
  const article = await loadArticle();

  schedule(() => sendMetric({ type: 'article_view', id: article.id }));
  return article;
}
```

В браузере `schedule` может использовать очередь бездействия, задачу после
первого отображения или другой механизм, подходящий продукту. На сервере
нельзя бездумно запускать клиентский API: нужно передать серверный планировщик
или отключить клиентскую интеграцию. Событие просмотра также может требовать
согласия пользователя и повторной защиты от дублей. Если выбранный планировщик
не обрабатывает отклонённые `Promise`, эту обработку нужно добавить на его
границе до запуска callback.

SEO-метаданные для статьи относятся к критическому пути, если они нужны
поисковой выдаче. Внешний виджет, техническая аналитика и необязательная
реклама обычно нет. Это не правило по названию библиотеки: решение следует
подтвердить профилированием и требованиями сценария.

Цена хорошего варианта — событие может не отправиться при закрытии страницы,
а порядок становится асинхронным. Для важных данных применяют очередь,
надёжную отправку при уходе со страницы или серверный сбор — в зависимости от
требований и приватности.

## Сравнение и ограничения

Ожидать аналитический вызов разумно, если без его результата нельзя принять
решение о содержании или если это часть обязательной операции. Для метрики
просмотра такое ожидание обычно ухудшает пользовательский путь. Отложенная
работа не должна скрывать ошибки, блокировать клавиатурную навигацию или
отправлять данные без необходимого согласия.

SSR помогает показать HTML раньше, но может увеличить работу сервера и не
устраняет тяжёлую гидрацию. Маленький JavaScript-файл не гарантирует быстрый
первый экран, если сеть ждёт шрифт или блокирующий ресурс. Сначала определите
показатель и базовое значение, затем меняйте один фактор и сравнивайте на
целевых устройствах.

## Упражнение

Создайте локальный `schedule`, который складывает переданную функцию в массив.
Проверьте, что после `await loadPage(...)` статья доступна, а массив содержит
одно событие, которое можно выполнить отдельно. Затем придумайте случай, когда
аналитика должна быть критичной, и обоснуйте, почему для него порядок нужно
изменить.

## Публичная проверка

В примере используются синтетическая статья и событие `article_view`; внешний
сервис не вызывается. Функции можно проверить через `node --check` и локальный
планировщик. Технические утверждения сверены с [web.dev о пользовательских
метриках](https://web.dev/articles/user-centric-performance-metrics),
[документацией Nuxt 4 о SEO и метаданных](https://nuxt.com/docs/4.x/getting-started/seo-meta)
и [документацией Nuxt 4 о рендеринге](https://nuxt.com/docs/4.x/guide/concepts/rendering).
