# Часть 6. TypeScript, тестирование и code review

## Учебная цель

После этой главы вы сможете сделать контракт входных данных явным, выделить
чистую функцию и выбрать тест, который проверяет не только удачный случай.
Нужны базовые JavaScript и понимание функций; синтаксис TypeScript будет
объяснён до примера.

## Ситуация и риск для пользователя

В карточке товара цена иногда отображается, а иногда страница падает после
изменения ответа сервера. Разработчик видит зелёный сценарий теста и считает
задачу закрытой, хотя пустое название или строковая цена никогда не
проверялись. Пользователь получает ошибку, а ревьюер вынужден восстанавливать
контракт по косвенным признакам.

## Термины

**Статическая типизация** описывает допустимые формы данных до запуска.
**Контракт** — договор о входе, выходе и ошибках функции. `any` отключает
проверку типа для значения. **Чистая функция** при одинаковом входе даёт тот
же результат и не меняет внешнее состояние.

**Unit-тест (модульная проверка)** проверяет небольшую единицу отдельно.
**Assertion (утверждение)** сравнивает фактический результат с ожидаемым.
Code review — проверка изменения другим человеком или агентом по понятным
критериям риска, а не по предпочтению оформления.

## Минимальная задача

Оба варианта формируют подпись карточки по объекту товара. Вход должен иметь
`title` и `priceCents`, результат — строка. Проверка включает обычную цену и
нулевую цену. Перед запуском сохраните пример как `example.ts` и выполните
`npx tsc --noEmit --strict example.ts`.

## Плохой пример

`any` иногда используют, чтобы быстрее принять ещё не согласованный ответ
сервера:

```ts
function cardLabel(item: any) {
  return `${item.title} — ${(item.priceCents / 100).toFixed(2)} ₽`;
}

if (cardLabel({ title: 'Книга', priceCents: 129900 }) !== 'Книга — 1299.00 ₽') {
  throw new Error('unexpected label');
}
```

Удачный случай проходит, но контракт не виден. Объект без `title` даст строку
`undefined`, а строковая цена вызовет ошибку только во время работы. Единственная
проверка не говорит, как функция должна вести себя на нулевой цене. Такой код
может появиться в рабочей ветке, когда тип ответа ещё обсуждается, но его риск
нельзя оставлять без срока и владельца.

## Хороший пример

Тип описывает минимальный контракт, а чистая функция легко проверяется без
компонента и сети:

```ts
type Product = {
  title: string;
  priceCents: number;
};

function cardLabel(item: Product): string {
  return `${item.title} — ${(item.priceCents / 100).toFixed(2)} ₽`;
}

function assertEqual(actual: string, expected: string): void {
  if (actual !== expected) {
    throw new Error(`Expected ${expected}, received ${actual}`);
  }
}

assertEqual(cardLabel({ title: 'Книга', priceCents: 129900 }), 'Книга — 1299.00 ₽');
assertEqual(cardLabel({ title: 'Закладка', priceCents: 0 }), 'Закладка — 0.00 ₽');
```

Теперь редактор и компилятор видят форму входа. Тест проверяет результат и
границу, а не устройство компонента. Это не означает, что тип гарантирует
правдивость данных из сети: на внешней границе нужен runtime-парсер или
проверка ответа.

Цена — нужно договориться о единицах цены, валюте и правилах округления.
Символ `₽` в маленьком синтетическом примере удобен для ясности, но реальный
продукт может принимать валюту параметром и форматировать её по локали.

## Сравнение и ограничения

`any` полезен как временная граница при миграции, если место помечено и имеет
план удаления. Для нового контракта он скрывает слишком много. Unit-тест
быстрее сценария браузера, но не проверяет доступность, интеграцию компонента
или настоящий ответ сервера. Нужный уровень проверки определяется риском.

При code review спросите: что произойдёт при пустом входе, кто проверяет
внешние данные, можно ли повторить тест без сети и какое поведение изменилось.
Если ответ нельзя получить из типа, кода или теста, это повод уточнить
контракт.

## Упражнение

Добавьте поле `currency` и измените контракт так, чтобы функция не принимала
неизвестный код валюты. Напишите проверку для нулевой цены и для двух разных
валют. Затем проведите короткое ревью плохого варианта: назовите два риска,
которые видны из кода, и один вопрос, на который нужна информация от владельца
API.

## Публичная проверка

Данные `Книга`, `Закладка` и цены вымышлены, сеть не используется. TypeScript-
пример проверяется командой `npx tsc --noEmit --strict example.ts`, а assertions
проверяют ожидаемое поведение при запуске скомпилированного файла. Термины
сверены с [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/2/basic-types.html)
и [руководством Vitest](https://vitest.dev/guide/).
