# Часть 7. Доставка, окружения и эксплуатация

## Учебная цель

После этой главы вы сможете различить настройки сборки и запуска, спроектировать
минимальную проверку живого SSR-процесса и объяснить, почему успешная сборка
не равна готовому релизу. Предварительный опыт Docker не нужен.

## Ситуация и риск для пользователя

После релиза страница открывается, но обращается к сервису из тестового
окружения. Либо оркестратор считает процесс исправным, хотя приложение не
может принять запросы, и направляет к нему пользователей. Для человека это
ошибка данных или недоступная страница; для команды — непредсказуемая граница
между сборкой и запуском.

## Термины

**SSR (server-side rendering, серверный рендеринг)** — подготовка HTML на
сервере до загрузки клиентского JavaScript. Такой режим требует запускать
серверную часть приложения, а не только отдавать статические файлы.

**Сборка (build)** создаёт артефакт приложения. **Runtime** — время, когда
процесс уже запущен и обслуживает запросы. **Образ контейнера** — шаблон,
содержащий приложение и инструкции запуска; контейнер — работающий экземпляр
образа.

**Nuxt `runtimeConfig`** — конфигурация, объявленная в `nuxt.config.ts` и
доступная во время запуска. Поля `public` могут попасть в браузер, остальные
поля предназначены для серверной стороны.

**Nitro** — серверный движок Nuxt, который собирает серверную часть и готовит
её для выбранной среды доставки. Для SSR на Node.js результатом обычно служит
собранная точка запуска, а не исходная папка приложения.

**Production entrypoint (точка запуска боевого процесса)** — конкретная
команда или файл, с которого стартует собранное приложение.

**`defineNuxtConfig`** — Nuxt-функция, возвращающая конфигурацию приложения.
**`useRuntimeConfig`** — Nuxt composable, через который код читает объявленную
конфигурацию во время запуска.

**Health check (проверка здоровья)** — запрос или команда, по которым система
оценивает процесс. **Liveness (живость)** отвечает на вопрос «процесс ещё
работает?». **Readiness (готовность)** — «можно ли сейчас направлять к нему
трафик?». **Rolling update** постепенно заменяет экземпляры, уменьшая риск
одновременной остановки всей службы.

## Минимальная задача

Оба варианта читают адрес прикладного сервиса и сообщают состояние процесса.
Вход — объект окружения. Результат — конфигурация и ответ проверки живости.
Локальная проверка передаёт два разных адреса без пересборки и проверяет, что
пустой адрес отклонён.

## Плохой пример

В небольшой команде адрес могут быстро записать в исходник, а проверку свести
к тому, что процесс отвечает:

```js
const buildConfig = {
  apiOrigin: 'https://api.example.invalid',
};

function liveness() {
  return { status: 200, body: 'process exists' };
}
```

Адрес теперь закреплён в артефакте сборки: один образ нельзя безопасно
использовать в нескольких окружениях. Проверка живости полезна, но ничего не
говорит о готовности приложения принять работу. Если конфигурация неверна,
процесс будет считаться здоровым, пока пользователи получают ошибки.

## Хороший пример

Адрес читается на запуске и валидируется один раз. Проверка живости остаётся
лёгкой, а готовность при необходимости проверяет зависимость отдельно.

```js
function readRuntimeConfig(env) {
  if (!env.PUBLIC_API_ORIGIN) {
    throw new Error('PUBLIC_API_ORIGIN is required');
  }

  return Object.freeze({ apiOrigin: env.PUBLIC_API_ORIGIN });
}

function liveness() {
  return { status: 200, body: 'ok' };
}

async function readiness(checkDependency) {
  const available = await checkDependency();
  return available
    ? { status: 200, body: 'ready' }
    : { status: 503, body: 'not ready' };
}
```

Один образ можно запустить с разными значениями окружения. `liveness` не
зависит от внешней сети и не вызывает перезапуск из-за временной ошибки.
`readiness` может убрать экземпляр из трафика, пока зависимость недоступна.
Конкретный оркестратор и правила ожидания выбираются отдельно.

Цена — ошибка конфигурации обнаруживается при запуске, а не при сборке, поэтому
нужны проверка окружения и понятный журнал старта. Слишком глубокая readiness-
проверка может вызвать каскадные перезапуски или скрыть частичную работу;
область проверки должна соответствовать обещанию сервиса.

## Как это выглядит в Nuxt 3 и Nuxt 4

Обобщённая функция `readRuntimeConfig` выше полезна для понимания идеи, но Nuxt
имеет собственный договор конфигурации. Значение нужно объявить в
`runtimeConfig`, а приложение читает его через `useRuntimeConfig`.

Плохой вариант фиксирует адрес в Nuxt-конфигурации:

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    public: {
      apiBase: 'https://api.example.invalid',
    },
  },
});
```

Такой код может работать локально, но адрес становится частью собранного
описания. Один артефакт нельзя безопасно перенести между окружениями без
пересборки, а публичное поле в любом случае доступно браузеру. В реальном
приложении это также создаёт риск случайно поместить секрет в `public`.

Хороший вариант объявляет форму конфигурации и оставляет значение для запуска:

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: '',
    public: {
      apiBase: '',
    },
  },
});
```

Сервер получает значения через переменные окружения, соответствующие ключам,
например `NUXT_API_SECRET` и `NUXT_PUBLIC_API_BASE`; клиент видит только
`runtimeConfig.public.apiBase`:

```ts
const config = useRuntimeConfig();
const apiBase = config.public.apiBase;
```

Второй фрагмент относится к коду приложения и не должен читать `apiSecret` в
браузере. Точная схема окружения и способ передачи переменных зависят от
платформы, поэтому проверяйте их на запущенном артефакте, а не только в
локальном файле `.env`.

Для SSR-сборки на Node.js последовательность выглядит так:

```bash
nuxt build
NODE_ENV=production node .output/server/index.mjs
```

`nuxt build` создаёт результат Nitro, а вторая команда запускает его как
сервер. Если приложение полностью предварительно генерируется для статической
доставки, Node entrypoint не нужен; это другое решение с другими ограничениями
для динамических данных.

В Nuxt 3 эти файлы и команды образуют привычный SSR-путь. При переходе на
Nuxt 4 дополнительно проверяют структуру `app/`, но `runtimeConfig` и
серверный entrypoint нельзя считать автоматически проверенными одной
перестановкой каталогов. Сверьте переменные окружения, production-сборку,
проверку готовности и реальный способ запуска.

## Сравнение и ограничения

Встраивание значения на build-time допустимо для действительно неизменяемого
публичного ресурса. Для адресов и флагов, меняющихся между окружениями,
runtime-подход уменьшает число разных артефактов. Секреты не следует помещать
в клиентский код: то, что отправлено браузеру, нельзя считать секретным.

Для статического сайта процессной liveness может не быть. Для SSR-приложения
процесс Node.js — часть продукта, и его запуск, память, остановка и обновление
нужно учитывать. Health check не заменяет мониторинг, журналирование и
проверку пользовательского сценария после релиза.

## Упражнение

Вызовите `readRuntimeConfig` с двумя объектами окружения и убедитесь, что
результаты различаются без изменения функции. Добавьте локальный
`checkDependency`, который возвращает `false`, и объясните, почему его статус
должен быть `503`, а не ошибка живости. Составьте список из трёх проверок перед
постепенным обновлением контейнера.

## Публичная проверка

Адрес `api.example.invalid` и имя `PUBLIC_API_ORIGIN` синтетические; секреты,
внутренние хосты и настройки инфраструктуры отсутствуют. Код автономен и
проверяется через `node --check` и вызовы с локальными объектами окружения.
