# Часть 8. Устойчивые UI-решения и паттерны Vue

## Ситуация и риск для пользователя

Пользователь нажимает «Удалить». Окно подтверждения открывается, но после
перехода по странице его кнопка закрытия не меняет состояние, клавиша Escape
оставляет затемнение, а повторное открытие показывает старый идентификатор.
Пользователь не понимает, какое действие сейчас подтверждает. Причина часто в
том, что страница и само окно хранят разные флаги.

## Учебная цель

После этой главы вы сможете выбрать источник правды для popup-состояния,
описать его переходы и понять, когда composable или управляемый компонент
уменьшает связанность интерфейса. Нужны базовые JavaScript и условный
рендеринг.

## Термины

**Popup или modal (всплывающее окно)** — временный слой интерфейса,
перехватывающий внимание и действие пользователя. **Источник правды** — одно
место, из которого остальные части получают актуальное состояние.
**Конечный автомат** описывает допустимые состояния и переходы между ними.

**Composable** — переиспользуемая функция, объединяющая состояние и операции
Vue. **Controlled component (управляемый компонент)** получает значение и
сообщает о намерении изменить его владельцу. **Teleport** переносит DOM-узел
окна в подходящий контейнер, но не должен скрывать его жизненный цикл.

**Payload** — данные, относящиеся к конкретному открытому окну; в примере это
идентификатор и заголовок записи.

## Минимальная задача

Оба варианта открывают окно подтверждения с `{ id, title }`, закрывают его по
действию пользователя и очищают старые данные. Вход — идентификатор и
заголовок записи. Результат — состояние окна. Проверка выполняет открытие,
повторное открытие другой записью, закрытие и Escape.

## Плохой пример

Разработчик может оставить флаг на странице и добавить ещё один в компоненте
окна, чтобы не менять существующий интерфейс:

```js
function createBadPopupFlow() {
  let pageOpen = false;
  let popupOpen = false;
  let selectedId = null;

  return {
    open(id) {
      selectedId = id;
      pageOpen = true;
      popupOpen = true;
    },
    closeFromPopup() {
      popupOpen = false;
    },
    view() {
      return { pageOpen, popupOpen, selectedId };
    },
  };
}
```

После `closeFromPopup` страница всё ещё считает окно открытым. При следующем
рендере два потребителя могут выбрать разные ветки, а `selectedId` остаётся
даже после закрытия. Это не абстрактная ошибка: она появляется естественно,
когда компонент пытаются сделать самостоятельным без договора о владельце
состояния.

## Хороший пример

Один менеджер хранит состояние, а все действия проходят через явные операции.
Компонент Vue может использовать его внутри composable, а `Teleport` — только
изменить место DOM-отрисовки.

```js
function createPopupStore() {
  let state = { kind: null, payload: null };
  const close = () => {
    state = { kind: null, payload: null };
  };

  return {
    open(kind, payload) {
      state = { kind, payload: { ...payload } };
    },
    close,
    onKey(key) {
      if (key === 'Escape') close();
    },
    snapshot() {
      return {
        kind: state.kind,
        payload: state.payload ? { ...state.payload } : null,
      };
    },
  };
}

const popup = createPopupStore();
popup.open('remove-record', { id: 'record-7', title: 'Черновик' });
```

Теперь закрытие очищает и видимость, и payload. В Vue компонент может получать
`snapshot()` как управляемое значение и сообщать `close` владельцу. Для
доступности нужно дополнительно вернуть фокус на инициатор, ограничить его
внутри модального окна и связать окно с понятным заголовком. Блокировка
прокрутки и слой отображения также являются отдельными решениями.

Цена централизованного менеджера — его API нужно поддерживать, а слишком
много разных popup-типов может превратить состояние в неясный список. Для
диалога, который используется только в одном компоненте, локальное состояние
проще и безопаснее.

## Сравнение и ограничения

Дублирование состояния быстро становится опасным, если окно открывается из
нескольких мест, сохраняет payload или должно закрываться глобальным событием.
Для одного небольшого блока дополнительный store не нужен. Composable хорош,
когда нужно повторить поведение, но он не должен скрывать неожиданные
побочные эффекты и доступ к глобальным данным.

`defineModel` или другой механизм управляемого значения удобен, когда владелец
должен контролировать состояние поля. `defineExpose` подходит для редкого
императивного действия, например фокусировки, но не должен заменять обычные
события. Любой паттерн следует выбирать по проблеме, а не по названию.

## Упражнение

Добавьте в менеджер действие `replace`, которое меняет payload без закрытия.
Проверьте, что повторное открытие другой записи не показывает прежний
заголовок, закрытие очищает состояние, а `Escape` даёт тот же результат.
Затем перечислите три требования доступности, которые нельзя доказать одной
проверкой `snapshot()`.
