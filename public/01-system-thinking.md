# Часть 1. Как мыслить о frontend-системе

## Ситуация и риск для пользователя

Представьте страницу статьи. Пользователь нажимает «Открыть», но в одном
окружении кнопка обращается не туда, в другом адрес приходится менять в коде,
а при серверном рендеринге появляется лишняя задержка. Для пользователя это
выглядит как сломанная ссылка или бесконечное ожидание. Для команды проблема
начинается с маленькой строки, в которой интерфейс одновременно знает адрес
сервиса, формат URL и способ запроса.

Архитектура — это не перечень папок, а договор о том, где принимаются решения.
Если UI отвечает сразу за разметку, транспорт и окружение, каждое изменение
увеличивает число мест, которые нужно проверить.

## Учебная цель

После этой главы вы сможете провести границу между интерфейсом,
конфигурацией и прикладной операцией в небольшой SSR-системе. Предполагается,
что вы знаете базовый JavaScript и умеете читать простой компонент Vue.

## Термины

**UI (user interface, пользовательский интерфейс)** — видимая часть
приложения, с которой взаимодействует человек.

**API (application programming interface, программный интерфейс)** — договор
о том, как одна часть системы обращается к другой и какой результат получает.

**URL (uniform resource locator, адрес ресурса)** — строковый адрес, по
которому можно обратиться к странице или сетевому ресурсу.

**Сервис (service)** — часть прикладного кода, которая предоставляет операцию
через понятный договор и скрывает технические детали её выполнения.

**Граница ответственности** — место, где заканчивается одна обязанность и
начинается другая. Компонент отвечает за отображение и действия пользователя,
но не обязан знать внутренний адрес сервиса.

**SSR (server-side rendering, серверный рендеринг)** — подготовка HTML на
сервере до того, как браузер загрузит и активирует клиентский JavaScript. Это
может улучшить первое отображение, но добавляет серверный контекст и требует
осторожно обращаться с браузерными API.

**Hydration (клиентская активация)** — этап, на котором браузер связывает
заранее подготовленный SSR HTML с клиентским JavaScript, чтобы страница стала
интерактивной.

**Runtime configuration (конфигурация во время запуска)** — значения,
которые приложение получает при старте, а не встраивает навсегда в исходный
код. Адрес сервиса и режим окружения обычно относятся к этой категории.

**Координирующий слой** — функция или страница, которая связывает несколько
операций в пользовательский сценарий, не забирая на себя их внутреннюю
реализацию.

**Nuxt 3** — framework (каркас) поверх Vue, который задаёт соглашения для
страниц, серверного рендеринга, загрузки данных, плагинов и серверной части
приложения. В этой книге Nuxt 3 — основная среда примеров. Архитектурные
выводы при этом применимы и к другим SSR-фреймворкам, если у них есть те же
границы между UI, сервером и конфигурацией.

**Nuxt 4 directory structure (структура каталогов Nuxt 4)** — соглашение, в
котором код приложения по умолчанию собран под каталогом `app/`, а `server/`,
`public/`, конфигурация и другие корневые области остаются рядом с ним.

**`srcDir`** — настройка, указывающая Nuxt, где находится исходный код
приложения. Явное значение этой настройки может изменить путь, который Nuxt
считает каталогом приложения, поэтому его нужно проверить перед миграцией.

**`shared/`** — место для кода, который может использоваться несколькими
средами. Такой код не должен зависеть от Vue, браузерных API или серверного
runtime, если его предполагается выполнять и на сервере, и в браузере.

**`useFetch` и `useAsyncData`** — Nuxt-инструменты загрузки данных, которые
связывают серверное получение данных с клиентской активацией. Прямой `$fetch`
в setup-коде компонента (коде, который выполняется при его настройке) может
привести к повторному запросу после SSR, поэтому способ
загрузки тоже проверяют при переходе между версиями.

**Diff (список изменений)** — результат сравнения двух версий файлов. Его
читают после автоматического преобразования, чтобы увидеть не только успешную
сборку, но и неожиданные изменения.

**Composables (переиспользуемая логика Vue)** — функции, которые объединяют
реактивное состояние и операции для повторного использования в компонентах.

**Plugins (плагины)** — подключаемые модули, которые настраивают общую
инфраструктуру приложения при его запуске.

**Middleware (промежуточная проверка)** — функция, которая выполняется на
границе навигации или другого процесса и может разрешить, изменить или
остановить его продолжение.

## Минимальная задача

Оба варианта должны построить адрес статьи по идентификатору и вернуть его для
действия пользователя. Вход — объект конфигурации с `apiOrigin` и строковый
идентификатор. Результат — корректный URL. Локальная проверка: передайте
разные адреса окружения и идентификатор с пробелом.

## Плохой пример

Такой код легко появляется в первой версии экрана: разработчику нужно быстро
проверить запрос, и адрес кажется частью конкретной кнопки.

```js
function articleButton(articleId) {
  const url = `https://api.example.invalid/articles/${articleId}`;
  return `<button data-url="${url}">Открыть статью</button>`;
}
```

На первый взгляд задача решена. Но разметка теперь знает о транспорте и
формате адреса. Идентификатор с кавычкой или пробелом не кодируется, адрес
нельзя сменить без изменения исходного текста, а серверная и клиентская части
могут начать строить разные ссылки. Исправление одной кнопки не гарантирует,
что остальные экраны используют тот же способ.

## Хороший пример

Сначала создаётся маленький объект прикладной конфигурации, затем отдельная
функция строит URL. Компоненту остаётся получить готовый результат и решить,
как его показать.

```js
function createArticleLinks({ apiOrigin }) {
  if (!apiOrigin) throw new Error('apiOrigin is required');

  return {
    byId(articleId) {
      const path = `/articles/${encodeURIComponent(articleId)}`;
      return new URL(path, apiOrigin).toString();
    },
  };
}

function articleButton(articleId, links) {
  return `<button data-url="${links.byId(articleId)}">Открыть статью</button>`;
}
```

Теперь граница видна: `createArticleLinks` отвечает за конфигурацию и URL,
`articleButton` — за небольшой фрагмент UI. Один и тот же объект ссылок можно
передать странице, сервису или тесту. В SSR важно создавать зависимость в
контексте текущего запуска и не хранить изменяемые данные запроса в общем
модуле.

Цена улучшения — дополнительное имя и необходимость передать зависимость.
Зато проверка становится прямой: для теста не нужен настоящий сервер, а
смена окружения не требует редактировать компонент.

## Сравнение и ограничения

Плохой вариант короче и может быть приемлем для одноразового статического
макета. Он становится рискованным, когда адрес используется более одного раза,
меняется между окружениями или код выполняется и на сервере, и в браузере.

Хорошая граница не означает, что каждую строку нужно помещать в отдельный
слой. В маленьком виджете функции можно оставить рядом, если их обязанность
очевидна и тест не требует настоящего сервиса. Главный критерий — не размер
файла, а ясность решений и возможность заменить окружение без изменения UI.

Полезно проверить три вопроса:

- может ли компонент работать с тестовой конфигурацией;
- кодируется ли вход, который контролирует пользователь;
- не хранит ли серверное выполнение данные одного запроса в общей переменной.

## Nuxt 3 как исходная точка и переход к Nuxt 4

В качестве основы возьмём Nuxt 3. Он поддерживает SSR-приложения, в которых страницы,
компоненты, composables, plugins, middleware и серверную среду выполнения
(runtime) образуют одну систему. Поэтому советы о состоянии, API и
эксплуатации в следующих частях
нужно читать с учётом того, что часть кода выполняется на сервере, а затем
активируется в браузере.

При этом Nuxt не требует запоминать все каталоги сразу. Сначала достаточно
различать код приложения и корневые технические области. В старой структуре
Nuxt 3 учебное приложение может выглядеть так:

```text
reading-app/
├── assets/
├── components/
├── composables/
├── layouts/
├── middleware/
├── pages/
├── plugins/
├── utils/
├── app.vue
├── nuxt.config.ts
├── public/
└── server/
```

Это небольшая учебная схема. Она нужна, чтобы понять направление изменений:
в Nuxt 4 код интерфейса и приложения по
умолчанию собирается под `app/`, а серверные обработчики и статические файлы
остаются корневыми областями.

## Небольшая задача миграции

Представьте, что вы обновляете это учебное приложение. Пользователь должен
по-прежнему открыть список статей, а команда — получить понятную границу
между кодом приложения и техническими каталогами. Это одна задача миграции:
изменить расположение кода и сохранить поведение SSR.

### Плохой пример: перенести всё под `app/`

Такой план может появиться из доброго намерения: разработчик видит новое
правило «код приложения находится в `app/`» и перемещает туда все каталоги
одной операцией.

```text
reading-app/
└── app/
    ├── components/
    ├── pages/
    ├── public/
    └── server/
```

Проблема обнаружится не обязательно сразу. Публичный файл может перестать
отдаваться по ожидаемому адресу, серверный обработчик — не попасть в
серверную среду выполнения, а локальная разработка и сборка для боевого
окружения начнут видеть
разную структуру. Если после этого исправлять только появившиеся ошибки, легко
потерять исходную причину и получить неполную миграцию.

Ещё один риск — бездумно заменить пути в импортах и тестах. Псевдоним пути
(alias) `~` обычно
продолжает указывать на каталог приложения, но ручные относительные пути,
настройки инструментов и тесты могли рассчитывать на прежнее расположение.

### Хороший пример: разделить код приложения и корень

Сначала зафиксируйте исходное дерево и значение `srcDir`, если оно задано
явно. Затем перенесите только каталоги самого приложения (app-side):

```text
reading-app/
├── app/
│   ├── assets/
│   ├── components/
│   ├── composables/
│   ├── layouts/
│   ├── middleware/
│   ├── pages/
│   ├── plugins/
│   ├── utils/
│   └── app.vue
├── nuxt.config.ts
├── public/
├── server/
└── shared/
```

Временная явная настройка может выглядеть так:

```ts
export default defineNuxtConfig({
  srcDir: 'app/',
});
```

В Nuxt 4 каталог `app/` является значением по умолчанию, поэтому этот ключ
не всегда нужно добавлять. Если в существующем приложении уже есть особый
`srcDir`, решение принимают после проверки его влияния, а не по одному имени
папки.

Команды обновления — только часть работы:

```bash
npm install nuxt@^4.0.0
npx codemod@latest nuxt/4/file-structure
```

`codemod` — инструмент автоматического преобразования исходных файлов. Он
может ускорить механическую перестановку, но не заменяет чтение diff,
проверку конфигурации и запуск тестов. Если текущая структура устраивает
команду, миграцию каталогов можно отложить: Nuxt 4 поддерживает старую схему
совместимости. Это снижает объём изменения, но оставляет прежнюю границу
между приложением и корнем.

Код, который действительно общий для серверной и клиентской сторон, можно
поместить в `shared/`. Он должен оставаться независимым от конкретного
runtime:

```ts
export function normalizeTitle(value: string): string {
  return value.trim().replace(/\s+/g, ' ');
}
```

Такая вспомогательная функция (utility) не знает о Vue и не читает `window`.
Если в `shared/` положить
переиспользуемую функцию (composable) с `ref` или импортом серверного модуля, граница снова станет
неясной: код перестанет быть безопасным для обеих сред.

### Вторая проверка миграции: SSR-загрузка данных

Перестановка каталогов не должна менять способ получения данных. В Nuxt 3 и
Nuxt 4 прямой вызов `$fetch` внутри setup-кода может выполниться при SSR и
повториться в браузере. Для данных страницы обычно выбирают `useFetch` или
`useAsyncData`, чтобы Nuxt связал серверный результат с hydration.

Плохой вариант выглядит коротко:

```vue
<script setup>
const articles = await $fetch('/api/articles');
</script>
```

Он может быть достаточен для маленького клиентского виджета, но для SSR-страницы
создаёт риск повторного запроса и разного поведения во время первого показа.

Хороший вариант задаёт одного владельца загрузки:

```ts
export function useArticleList() {
  return useFetch('/api/articles', {
    key: 'article-list',
  });
}
```

Компоненты получают результат `useArticleList`, а не дублируют `$fetch`.
Явный ключ помогает разделять или переиспользовать данные намеренно, но все
вызовы с одним ключом должны иметь совместимые настройки. Если одному экрану
нужны совсем разные параметры, ключ должен это отражать.

### Что проверить после перехода

Проверка должна отвечать не только на вопрос «собирается ли проект».
Для небольшого учебного приложения достаточно такого списка:

1. Сравнить дерево до и после и убедиться, что `public/` и `server/` находятся
   в корне, а общий код в `shared/` не импортирует Vue или серверную среду
   выполнения.
2. Проверить, что страницы и компоненты находятся под выбранным `srcDir`, а
   `~` и относительные импорты разрешаются одинаково в сборке и тестах.
3. Выполнить `nuxt prepare`, сборку для боевого окружения и тесты; отдельно открыть
   страницу через SSR и проверить, что клиентская активация не создаёт
   повторный запрос без причины.
4. Просмотреть изменения имён компонентов в тестах и `KeepAlive` (механизме
   сохранения экземпляров компонентов): при
   обновлении нормализация имён может изменить ожидания тестов.
5. Зафиксировать откат: если сторонний модуль или собственная настройка не
   готовы к Nuxt 4, временно сохранить старую структуру и обновить только
   зависимость после отдельной проверки.

Официальное [руководство Nuxt 4 по обновлению](https://nuxt.com/docs/4.x/getting-started/upgrade)
описывает перемещение каталогов приложения, сохранение корневых областей,
совместимость со старой структурой и codemod. Статус поддержки Nuxt и
совместимость модулей меняются, поэтому перед обновлением сверяйте актуальные
рекомендации и матрицу зависимостей.

Цена хорошей миграции — время на инвентаризацию, отдельную ветку и проверку
SSR. Цена быстрого переноса — ошибки, которые видны только в боевом окружении
или
только после активации страницы. Универсального правила «всегда переносите
всё в `app/`» нет: решение зависит от текущего `srcDir`, модулей, тестов и
готовности команды сопровождать новую структуру.

## Упражнение

Измените хороший пример так, чтобы он принимал необязательный префикс языка,
например `ru`, и строил `/ru/articles/...`. Проверьте, что пустой префикс не
создаёт двойной слеш, а идентификатор `a b` превращается в безопасную часть
URL. Затем объясните, где должна находиться проверка допустимого языка: в UI,
в прикладной функции или на сервере. Для самопроверки миграции нарисуйте
дерево своего небольшого учебного приложения в двух вариантах и отметьте
стрелками, какие каталоги должны остаться в корне. В отдельном абзаце
объясните, почему ваш `useFetch` или `useAsyncData` не создаёт лишний запрос
после SSR.
