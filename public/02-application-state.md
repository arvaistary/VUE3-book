# Часть 2. Состояние приложения и SSR

## Учебная цель

После этой главы вы сможете выбрать место для локального, общего и
производного состояния и объяснить, почему серверное приложение не должно
делить изменяемый список между запросами. Нужны базовые JavaScript и Vue.

## Ситуация и риск для пользователя

Пользователь добавляет товар в корзину и видит одну позицию. Другой человек
открывает страницу почти одновременно и видит ту же позицию, хотя ничего не
выбирал. Другая распространённая проблема выглядит мягче: значок корзины
показывает три позиции, а сама корзина содержит две. В обоих случаях
интерфейс сообщает противоречивую правду.

Состояние (state) — данные, от которых зависит текущий интерфейс и которые
могут измениться. Локальные данные одного компонента не нужно делать общими.
Но состояние, которым пользуются шапка, корзина и страница заказа, должно иметь
понятный источник правды.

## Термины

**Локальное состояние** принадлежит одному компоненту или сценарию и не
должно переживать его уничтожение.

**Общее состояние (shared state)** нужно нескольким потребителям. **Store
(хранилище)** — объект или модуль с таким состоянием и операциями его
изменения.

**Производное значение (derived state)** вычисляется из источника правды.
Количество товаров — производное значение списка, а не независимое число.

**Hydration (гидрация)** — этап, когда браузер связывает полученный от
сервера HTML с клиентским приложением. Если сервер и клиент посчитали разные
значения, пользователь может увидеть скачок интерфейса или предупреждение.

Во время SSR один процесс может обслужить много запросов. Поэтому фабрика
состояния создаёт отдельный экземпляр для каждого запуска приложения.

## Минимальная задача

Оба варианта ведут список позиций корзины и показывают его размер. Вход —
идентификаторы товаров, результат — список и вычисленное количество.
Проверка должна создать два экземпляра состояния, добавить разные товары и
убедиться, что они не влияют друг на друга.

## Плохой пример

Разработчик может выбрать модульную переменную, потому что она доступна из
любого компонента и не требует настройки store.

```js
const items = [];
let itemCount = 0;

function addToCart(id) {
  items.push(id);
  itemCount += 1;
}

function cartView() {
  return { items, itemCount };
}
```

У решения две разные проблемы. На сервере `items` живёт дольше одного запроса:
один посетитель может оставить данные следующему. Кроме того, список и
`itemCount` обновляются разными операциями и могут рассинхронизироваться при
удалении или повторном добавлении. Объект выглядит простым, но его жизненный
цикл скрыт.

## Хороший пример

Фабрика создаёт независимое состояние. Количество не хранится отдельно, а
вычисляется из списка.

```js
function createCartState(initialItems = []) {
  let items = [...initialItems];

  return {
    add(id) {
      items = [...items, id];
    },
    remove(id) {
      items = items.filter((item) => item !== id);
    },
    snapshot() {
      return {
        items: [...items],
        itemCount: items.length,
      };
    },
  };
}
```

Во Vue такой объект может стать основой composable или store, а реактивность
будет добавлена средствами выбранного инструмента. Существеннее другое:
жизненный цикл экземпляра виден, а `itemCount` невозможно забыть обновить
отдельно. Сервер может создать фабрику для запроса, а клиент — долгоживущий
экземпляр приложения.

Цена — нужно явно решить, где создать и кому передать состояние. При большом
числе полей store может стать трудно обозримым, поэтому его лучше делить по
областям, а не складывать в него каждый флаг интерфейса.

## Сравнение и ограничения

Модульная переменная удобна для действительно неизменяемой константы или
кэша, жизненный цикл которого сознательно общий для процесса. Она не подходит
для пользовательских данных при SSR. Отдельный счётчик допустим, если это
самостоятельное серверное значение, но для длины списка он создаёт лишнюю
точку рассинхронизации.

Не следует хранить в общем store состояние наведения мыши или открытой
подсказки, если у них один потребитель. И наоборот, авторизацию, выбранную
локаль или корзину нельзя прятать в случайном локальном `ref`, если они нужны
нескольким частям приложения. Хранилище не заменяет серверную проверку:
клиентский список корзины — только отображение намерения пользователя.

## Упражнение

Добавьте в `createCartState` операцию очистки и напишите три проверки:

- удаление последней позиции даёт `itemCount: 0`;
- два экземпляра не разделяют массив;
- повторное чтение `snapshot()` не позволяет внешнему коду изменить внутренний список.

Затем назовите одно поле, которое в вашем текущем проекте должно быть
локальным, и одно — общим. Обоснуйте выбор количеством потребителей и сроком
жизни данных.

## Публичная проверка

Пример использует только вымышленные идентификаторы и локальную фабрику. Его
можно сохранить в файл и проверить через `node --check`, затем выполнить
проверку двух экземпляров через `node`. Понятия сопоставлены с [руководством
Vue по управлению состоянием](https://vuejs.org/guide/scaling-up/state-management.html)
и [описанием режимов рендеринга Nuxt](https://nuxt.com/docs/guide/concepts/rendering).
