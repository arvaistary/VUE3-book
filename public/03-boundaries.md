# Часть 3. Границы ответственности: API, сервисы и middleware

## Учебная цель

После этой главы вы сможете отделить пользовательский интерфейс от сетевого
транспорта, вынести прикладную операцию в сервис и объяснить, почему
middleware маршрута не является местом для всех API-вызовов. Достаточно знать
JavaScript и базовый HTTP.

## Ситуация и риск для пользователя

Пользователь открывает карточку статьи. Один экран показывает понятную ошибку
при недоступной сети, другой падает с необработанным исключением, а третий
повторяет собственную сборку URL и отправляет неверный параметр. Для команды
это означает, что изменение серверного контракта нужно искать по компонентам,
а не менять в одном месте.

## Термины

**Слой ответственности** — участок системы с одной основной обязанностью.
Компонент отображает состояние и принимает действия. **Service layer (слой
сервисов)** выражает прикладную операцию, например «получить краткую статью».
**Transport adapter (транспортный адаптер)** знает, как выполнить HTTP-запрос.

**UI (user interface, пользовательский интерфейс)** — видимая часть сценария,
через которую человек получает результат и запускает действие.

**Plugin (плагин)** подключает общую зависимость к приложению. **Interceptor
(перехватчик)** может централизованно обработать заголовки или технические
ошибки. **Middleware** выполняется вокруг навигации и решает, можно ли
продолжить переход; он не должен незаметно становиться вторым сервисным слоем.

## Минимальная задача

Оба варианта должны получить краткое описание статьи по идентификатору и
вернуть объект `{ title, excerpt }`. Входом служит строковый идентификатор и
функция транспорта. Проверка использует локальный транспорт, который не
подключается к сети, и отдельный вариант с ошибкой.

## Плохой пример

В обработчике кнопки удобно написать всё сразу: URL, запрос и преобразование
ответа находятся рядом с местом использования.

```js
async function onOpenArticle(articleId, show) {
  const response = await fetch(`https://api.example.invalid/articles/${articleId}`);
  const data = await response.json();
  show(data.title, data.excerpt);
}
```

Такой вариант правдоподобен для пробного экрана. Но UI знает адрес, формат
ответа и отсутствие ошибок. Идентификатор не кодируется, сетевой вызов нельзя
подменить в тесте, а одинаковые кнопки начнут расходиться. Если сервер вернёт
неуспешный ответ или изменит форму данных, пользователь получит необъяснимое
поведение.

## Хороший пример

Сервис говорит на языке прикладной операции, а транспорт передаётся ему как
зависимость.

```js
function createArticleService(request) {
  return {
    async getSummary(articleId) {
      const result = await request(`/articles/${encodeURIComponent(articleId)}`);

      if (!result.ok) {
        throw new Error('article request failed');
      }

      return {
        title: result.data.title,
        excerpt: result.data.excerpt,
      };
    },
  };
}

async function loadArticleForPage(service, articleId) {
  try {
    return { status: 'success', data: await service.getSummary(articleId) };
  } catch {
    return { status: 'error', message: 'Статью не удалось загрузить' };
  }
}

const localRequest = async (path) => ({
  ok: path === '/articles/intro',
  data: { title: 'Введение', excerpt: 'Короткое описание статьи' },
});

const service = createArticleService(localRequest);
```

Страница теперь получает `status` и решает, что показать. Сервис проверяет
контракт ответа, а транспорт можно заменить адаптером для SSR, браузера или
теста. Это добавляет небольшой слой и требует договориться о форме ошибки,
зато изменение HTTP-деталей не распространяется по UI.

Middleware здесь уместен для проверки маршрута: например, при отсутствии
необходимого признака навигация может быть остановлена или направлена на
страницу входа. Получение текста статьи остаётся ответственностью страницы и
сервиса. Такой порядок снижает вероятность циклических перенаправлений и
повторных запросов при каждой навигации.

## Сравнение и ограничения

Прямой `fetch` может быть хорошим выбором для маленького одноразового
примера. Когда операция повторяется, имеет разные реализации транспорта,
общий формат ошибки или серверный и клиентский контекст, выделение сервиса
окупается. Не стоит создавать сервис ради единственной константы и прятать в
нём разметку.

Плагин подходит для общей инфраструктуры: HTTP-клиента, логирования или
клиентского SDK. Прикладную операцию лучше оставить сервису. Interceptor
может добавить заголовок или нормализовать техническую ошибку, но не должен
решать, какую надпись показать пользователю.

## Упражнение

Добавьте в локальный транспорт ответ `{ ok: false }` и проверьте, что страница
получает `status: 'error'`, а не исключение наружу. Затем замените путь статьи
на идентификатор с пробелом и убедитесь, что сервис кодирует его. Наконец,
напишите псевдокод middleware для маршрута `/account`: перечислите условие,
действие при отказе и условие, которое исключает бесконечный redirect.

## Публичная проверка

`articles`, `api.example.invalid`, тексты и ответы полностью вымышлены.
Пример автономен: `createArticleService` использует локальный `localRequest`,
поэтому его можно проверить через `node --check` и последовательные вызовы без
внешнего API. Термины сверены с [документацией Nuxt о
плагинах](https://nuxt.com/docs/guide/directory-structure/plugins) и
[middleware](https://nuxt.com/docs/guide/directory-structure/middleware).
