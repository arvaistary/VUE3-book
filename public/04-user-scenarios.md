# Часть 4. Пользовательские сценарии: формы и авторизация

## Учебная цель

После этой главы вы сможете описать отправку формы как последовательность
наблюдаемых состояний, различить ошибки ввода и сервера и защитить действие
от повторной отправки. Нужны базовые JavaScript и понимание событий формы.

## Ситуация и риск для пользователя

Пользователь вводит адрес, нажимает кнопку и не видит реакции. Он нажимает
ещё раз, в результате получает два уведомления или сообщение «произошла
ошибка», хотя адрес уже был принят. Для человека непонятно, что произошло,
а команда не может отличить ошибку ввода от временной проблемы сервера.

## Термины

**Пользовательский сценарий** — последовательность действий, состояний и
результатов, через которую человек достигает цели. **Валидация** проверяет
форму на соответствие известным правилам. Клиентская валидация помогает дать
быструю подсказку, но серверная проверка всё равно обязательна.

**Состояние ошибки** должно сохранять не только факт неудачи, но и её смысл.
**Идемпотентность** означает, что повтор одной операции не создаёт
дополнительный нежелательный результат. Блокировка кнопки уменьшает число
повторов в UI, но не заменяет защиту операции на сервере.

## Минимальная задача

Оба варианта отправляют адрес для подписки на уведомления. Вход — строка и
функция `send`, результат — состояние `idle`, `loading`, `success` или
`error`. Локальная проверка вызывает `submit` дважды до завершения первого
запроса и отдельно проверяет неверный адрес и ответ сервера.

## Плохой пример

В маленькой форме можно начать с одной переменной и общего сообщения:

```js
function createBadForm(send) {
  let message = '';

  return {
    async submit(email) {
      if (!email.includes('@')) {
        message = 'Ошибка';
        return;
      }

      message = 'Загрузка';
      const result = await send(email);
      message = result.ok ? 'Готово' : 'Ошибка';
    },
    getMessage() {
      return message;
    },
  };
}
```

Форма выглядит рабочей, пока сеть отвечает мгновенно. Два вызова `submit`
могут выполняться одновременно и оба создать операцию. Пользователь не
понимает, исправим ли адрес или нужно повторить попытку, а код не различает
ошибку сервера и уже существующую подписку.

## Хороший пример

Состояние явно описывает этап операции, а повтор во время загрузки игнорируется.
Коды ответа преобразуются в сообщения на границе сценария.

```js
function createSubscriptionForm(send) {
  let state = { status: 'idle', message: '' };

  return {
    async submit(email) {
      if (state.status === 'loading') {
        return { status: 'ignored', message: 'Запрос уже выполняется' };
      }

      if (!/^\S+@\S+\.\S+$/.test(email)) {
        state = { status: 'error', message: 'Проверьте адрес электронной почты' };
        return state;
      }

      state = { status: 'loading', message: '' };
      let result;
      try {
        result = await send(email);
      } catch {
        state = { status: 'error', message: 'Сервис временно недоступен' };
        return state;
      }

      if (result.ok) {
        state = { status: 'success', message: 'Подписка создана' };
      } else if (result.code === 'already-subscribed') {
        state = { status: 'error', message: 'Этот адрес уже подписан' };
      } else {
        state = { status: 'error', message: 'Попробуйте ещё раз позже' };
      }

      return state;
    },
    getState() {
      return { ...state };
    },
  };
}
```

Такой контроллер не решает всю авторизацию, но показывает её важную идею:
«вход выполнен» — не единственное возможное состояние. В реальном сценарии
могут появиться истёкшая сессия, требование подтверждения и ограничение числа
попыток. Их стоит добавить в явный контракт, а не прятать в наборе
несвязанных булевых флагов.

Цена — больше состояний и необходимость согласовать тексты с дизайном.
Преимущество — каждое состояние можно проверить и связать с действием
пользователя. Сервер по-прежнему должен повторно проверить адрес, право и
идемпотентность операции.

## Сравнение и ограничения

Одна строка сообщения может быть достаточна для внутреннего прототипа, если
повторная отправка невозможна и сервер возвращает только один исход. Для
публичной формы с сетью и несколькими ошибками она скрывает важные переходы.

Регулярное выражение в примере — только быстрая подсказка, а не полный
стандарт адресов. Блокировка кнопки не защищает от двух вкладок, повторного
HTTP-запроса или сетевого повтора. Для критичной операции серверу нужен
идентификатор запроса или другой механизм идемпотентности.

## Упражнение

Создайте локальный `send`, который возвращает успех, затем
`already-subscribed`, затем временную ошибку. Для каждого ответа запишите
ожидаемые `status` и `message`. Отдельно вызовите `submit` дважды, задержав
завершение первого Promise. Проверьте, что второй вызов не отправляется.

## Публичная проверка

Пример не содержит данных реальных пользователей и не подключается к сервису.
Его можно проверить через `node --check`, передав локальные функции `send` для
трёх исходов и контролируемый Promise. Основы формы сверены с [MDN о работе с
формами](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms).
