# Adversarial review после реализации

Adversarial review — это проверка отрицательных и опасных сценариев после
реализации и до `hybrid-finalize`. Она дополняет тесты и не позволяет объявить
задачу готовой только потому, что happy path работает.

Канонический источник требований — `spec.md` активного work-item. Для brief
используйте сам brief.

## Обязательные проходы

### 1. Scope и provenance

- Сравните tracked и untracked diff с зафиксированным `base_ref`.
- Проверьте allowlist и denylist отдельно для итогового коммита.
- Не включайте в feature commit служебные файлы, workflow-изменения и
  несвязанную документацию, если этого нет в allowlist.
- Не считайте ignored-файлы доказательством чистоты: проверьте рабочую копию и
  staged paths физически.
- До финализации реализация должна быть закоммичена после `base_ref`, а
  рабочая копия — чистой.

### 2. Сверка источников истины

Для каждого важного требования пройдите цепочку:

```text
spec.md → plan.md/tasks.md → implementation → docs → named test → current evidence
```

Проверьте точный исход, actor fixture, endpoint, коды `401/403/404/409/422`,
приоритет ошибок, state predicate и отсутствие изменения данных при отказе.
Если включён `AUTH_MATRIX_ROW_COVERAGE: required`, каждая строка матрицы должна
иметь case ID и конкретный assertion, а каждый case ID — обратную ссылку.
Нерешённое расхождение запрещает `CONTRACT_RECONCILIATION=PASS` и
`ADVERSARIAL_REVIEW=PASS`.

### 3. Workflow и права

- Для каждой операции выпишите `actor × operation × expected outcome`.
- Проверьте обычного участника без доступа, бывшего владельца, отклонённого
  получателя и административный контекст, если они есть в задаче.
- Для каждого write-пути проверьте корректный и повреждённый ввод.
- Для каждой дочерней или составной мутации проверьте freeze, pending,
  удаление родителя, scoped `404`, порядок блокировок и неизменность данных.
- Убедитесь, что server-controlled fields нельзя передать через mass assignment.

### 4. Побочные эффекты

- Проверьте границу транзакции и момент запуска после commit.
- Проверьте rollback, повторную обработку и отсутствие дубликатов.
- Подтвердите реальную связку `producer → handler → transport`, а не только
  прямой вызов handler-а.
- Если payload ссылается на изменяемые записи, проверьте их удаление и
  недоступность либо передавайте безопасные scalar identifiers.

### 5. Concurrency и runtime

- Для lock/race-контракта local-only или skipped test не является PASS без
  явного обоснования в спецификации.
- Укажите фактический runtime, число повторений и результат победителя/проигравшего.
- Отсутствие обязательного runtime блокирует `READY`.

### 6. Capability и публичная безопасность

Если операция использует capability или публичную ссылку, проверьте формат и
entropy токена, hash-only хранение, одинаковый privacy-safe ответ для unknown,
expired, revoked и deleted, allowlist публичных полей и запрет обхода
авторизованной мутации.

### 7. Целостность доказательств

- Каждый маркер из `Hybrid required evidence` должен иметь в отчёте команду,
  имя теста или фактический runtime output.
- `PASS` нельзя ставить по наличию файла, старому отчёту или skipped test.
- Убедитесь, что в отчёте нет одновременно `KEY=PASS` и `KEY=FAIL` или
  `KEY=BLOCKED`.
- Разделяйте доказательства из текущего запуска и утверждения автора.

## Как оформить результат

Добавьте в DoD report короткую таблицу:

```markdown
| Проход | Что проверено | Доказательство | Статус |
|--------|---------------|----------------|--------|
| Scope | allowlist и clean worktree | команда и commit | Clear |
| Auth | actor × operation | named test | Clear |
| Evidence | все обязательные маркеры | Evidence Index | Clear |
```

Маркер `ADVERSARIAL_REVIEW=PASS` означает, что выполнены все семь проходов.
Для задачи с `CONTRACT_RECONCILIATION: required` добавьте также
`CONTRACT_RECONCILIATION=PASS`.
